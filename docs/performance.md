# Нагрузочная проверка

## Запуск

```bash
make test-load

# Проверка сценария на небольшой нагрузке:
LOAD_RATE=20 LOAD_SECONDS=5 LOAD_CONFLICT_SECONDS=2 make test-load

# Если Compose установлен отдельной командой:
make test-load COMPOSE=docker-compose
```

Нужен запущенный Docker с Compose. k6 2.3.0 закреплён по digest в
[docker-compose.load.yml](../docker-compose.load.yml). Запуск создаёт отдельный
Compose-проект с новой PostgreSQL и случайными портами. Пользовательский `.env`
не читается. Контейнеры, сеть и volumes этого проекта удаляются также при ошибке.

Параметры: `LOAD_RATE` — запросы/с (1–2000), `LOAD_SECONDS` — длительность
смешанной нагрузки (1–600), `LOAD_CONFLICT_SECONDS` — длительность конфликтной
нагрузки (1–120). Произведение первых двух должно делиться на 10. Это пределы
входных параметров, а не обещание выдержать любую такую нагрузку. Подготовка
большого количества подарков может превысить отведённые 120 секунд.

После прогона выводится путь к временной папке с `summary.json`, `k6.log`,
`services.log`, `environment.txt`, списком образов и копиями входных файлов.
Эти материалы сохраняются после удаления контейнеров. JSON-отчёт не содержит
JWT или публичных токенов подготовленных списков.

## Методика

1. Зарегистрировать владельца через API. Создать 20 рабочих вишлистов и 20
   отдельных вишлистов для гонок. В рабочих заранее забронировать по одному
   подарку и подготовить свободные подарки для каждой плановой новой брони.
2. Прогреть публичное чтение 5 секунд. Регистрация, подготовка и прогрев
   не входят в измерения смешанного профиля.
3. В течение 60 секунд отправлять 100 запросов/с. На каждые 10 запросов:
   5 публичных чтений списка с подарками, 2 чтения списка вишлистов владельца,
   1 PATCH описания вишлиста, 1 PATCH описания ранее забронированного подарка,
   1 новая бронь. Публичные запросы выполняются без JWT.
4. Отдельно 20 секунд отправлять 100 повторных броней/с одного занятого
   подарка. Требуется точный ответ `409 {"error":"item already reserved"}`.
5. В каждом из 20 отдельных списков одновременно отправить 8 броней одного
   подарка и 4 PATCH: по одному изменению названия и описания списка и подарка.
   Требуются одна успешная бронь, семь конфликтов и четыре успешных PATCH.
   Эти пакеты проверяют конкурентность, а не целевые RPS.
6. Перечитать данные через API: все плановые и исходные брони сохранились,
   неизменявшиеся поля остались прежними, оба поля каждого объекта после
   конкурентных PATCH сохранили новые значения.

[constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)
задаёт частоту старта итераций независимо от длительности ответа. В смешанной
и конфликтной фазе одна итерация — один HTTP-запрос. Между фазами есть 11 секунд
для завершения запросов; HTTP timeout — 10 секунд.

Успешный прогон требует 100% ожидаемых ответов с проверкой содержимого,
нулевого числа `dropped_iterations` и успешных проверок сохранённых данных.
Ожидаемые `409` учитываются отдельно и не повышают процент успешных `2xx`.
Допустимо от `rate × duration` до `rate × duration + 1` запросов: k6 может
запустить дополнительную итерацию на границе интервала. Недобор не допускается.

Выбранный ориентир задержки — **p95 < 200 мс** для смешанного профиля в целом
и каждого вида операции. Это критерий данного теста, а не SLA или требование
исходного задания. `request_ms` измеряет время вокруг HTTP-вызова со стороны k6,
включая соединение и получение тела, без проверки JSON. Отдельно сохраняются
p99 и max; жёсткий максимум 200 мс не гарантируется. Частоту смешанного профиля
следует считать по его объёму и длительности, поскольку `rate` счётчика k6
в JSON использует время всего теста, включая другие фазы и паузы.

## Проверки самого сценария

```bash
# Node.js 22+, без npm-зависимостей:
make test-load-script
```

Тесты исполняют настоящий код сценария с управляемыми HTTP-ответами. Они проверяют
обнаружение невалидного JSON, `null`, неверной структуры, `503`, неправильного
`409`, нуля или двух победителей брони, неправильного ответа PATCH и потери
данных после успешных записей. Проверяется отсутствие JWT и share token в JSON.
Эти тесты включены в CI. Полный нагрузочный прогон запускается отдельно.

Методика и runner адаптированы из [room-booking](https://github.com/DevDashkovsky/Room-booking):
сценарии, данные и проверки целостности соответствуют API Wishlist.

## Результат 29 октября 2026 года

Сценарий и приложение — ревизия `c8750d5`. Код API в рамках этой проверки
не менялся. SHA-256 сценария:
`7c3c54c83ab119f093f0a02a8d9cd7ed088d21577407763eb894cf674cfc9a8c`.

Среда: Colima на macOS/ARM64, Linux VM с 2 CPU и примерно 1,91 GiB памяти,
PostgreSQL 17-alpine, k6 2.3.0, пул API — 20 соединений. API, БД и генератор
работают в одной VM. БД новая: 40 вишлистов и 640 подарков, из которых 20
забронированы до нагрузки, 600 предназначены для смешанного профиля,
ещё 20 — для гонок.

| Операция | Запросов | Корректных ответов | p95, мс | p99, мс | max, мс |
|---|---:|---:|---:|---:|---:|
| Публичное чтение с подарками | 3001 | 100% | 3 | 4 | 11 |
| Списки владельца | 1200 | 100% | 3 | 4 | 9 |
| PATCH вишлиста | 600 | 100% | 4 | 5 | 7 |
| PATCH занятого подарка | 600 | 100% | 4 | 5 | 10 |
| Новая бронь | 600 | 100% | 4 | 4 | 11 |
| **Смешанный профиль** | **6001** | **100%** | **4** | **4** | **11** |

6001 запрос за 60 секунд — около 100,02 RPS. Пропущенных итераций — 0.
Конфликтный профиль: 2001/2001 ожидаемых ответов. Все 20 гонок прошли;
в каждой ровно одна бронь из восьми успешна. Все 140 проверок сохранённых
данных прошли, включая сохранение новых броней и обоих полей после PATCH.
24 проверки самого сценария также прошли.

На этом профиле ошибки API не воспроизвелись, оснований менять код ради
производительности по этому замеру нет. Результат относится к небольшой
новой БД и минутной нагрузке в локальной VM. Он не определяет предел RPS,
не подтверждает длительную доступность, производительность bcrypt-входа,
больших списков, внешней сети или другого оборудования.
